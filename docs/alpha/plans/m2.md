## 1. What the measurements say (2026-11-05, Metal, headless 2144x1206, Zermatt still)

| Fact | Number | Source |
|---|---|---|
| Clean 6-scene baseline, headless 2144x1206 | 13.6-16.7 fps (60-75 ms), p99 67-90 ms; Manhattan-class scenes not in set | `tools/perf_headless.sh`, `target/perf_2026-11-05_clean/` |
| GPU occupancy, Zermatt still | 92% of wall time, ~61 ms GPU per frame at 16 fps | `tools/gpu_passes.sh` (union of all GPU intervals) |
| So | **the GPU is the limit**, not the CPU or entity count (entities 1.3k-2.2k, fps flat across scenes) | |
| Share of GPU work | main opaque 26%, shadow cascades ~17%, early prepass 7%, clouds+sky ~4%, bloom/SSAO/TAA small; "Read/Write Surface" 20% is the headless offscreen copy (ignore for windowed) | same |
| Excluding headless copy | main opaque ~33%, shadows ~21%, prepass ~9% | same |

Correction (2026-11-05): an earlier version of this table said 72 fps / 13.5 ms GPU. That came from an
`EW_BISECT` "base" run in which no tiles had loaded (0 tris), and from dividing trace time by the wrong
frame count (~8 trace intervals per frame). Both are fixed; `gpu_sum.py` now divides by real frames and
prints occupancy.

Reading: **there is no single hot pass.** Cost is spread over geometry drawn several times (prepass +
main + 4 shadow cascades all draw the same 23-45 M triangles) and per-pixel work. M1 removed the CPU
side (entity count); what remains is GPU geometry and shading work, which is exactly what M2 attacks:
draw geometry once, cull on the GPU, shade each pixel once, cache what doesn't change.

Open items before trusting absolute numbers: the first baseline (19-22 fps) ran while a windowed game
was open and is discarded; the headless number does not equal the windowed number (swapchain, display
scale, vsync). A windowed pass on the Mac (menu closed, nothing else running) is the final judge.

## 2. Rules that keep the Metal switch cheap

These are design constraints on `ed_gpu`/`ed_render`, checked in review.

1. **`ed_render` imports only `ed_gpu`.** No `wgpu::` or Bevy render types in `ed_render`.
2. **Resource model is native-shaped, not wgpu-shaped.** Resources live in large pooled buffers/textures
   addressed by index (bindless tables for textures and materials; one vertex/index/cluster pool per
   kind). A "draw" is an entry in a GPU-written indirect list. wgpu gets an emulation (multi-draw loop,
   binding arrays); Metal gets argument buffers + indirect command buffers.
3. **A pass graph, not ad-hoc encoders.** Each pass declares reads, writes and whether its targets are
   transient. wgpu executes it plainly; Metal can alias memory, keep targets in tile memory, and run
   independent passes on a second queue. Passes carry a name; every backend records per-pass GPU time.
4. **Shaders are MSL now**, kept in simple, portable style (no Apple-only tricks outside `Caps`-gated
   files). Windows (N7) gets a translation path. Anything needing 64-bit atomics, mesh shaders, RT or
   tile memory is behind an `ed_gpu::Caps` flag with a portable fallback.
5. **Timers are part of the API.** `ed_gpu::PassTimer` per pass. wgpu backend: render-pass
   `timestamp_writes` (works on Metal, unlike in-encoder writes); Metal backend: sample buffers.
6. **Upscaler is an interface from day one** (`Upscaler::{color, depth, motion, jitter, exposure}`);
   own TAAU is backend zero; MetalFX / DLSS / FSR3 are later backends.
7. **No per-tile entities in `ed_render`.** Tiles are data in GPU pools (see slice S7).

## 3. Integration

`ed_metal` (native Metal, objc2-metal) implements the `ed_gpu` interfaces and executes the pass graph.
Until the cutover (N6) the Bevy renderer keeps drawing the real game so nothing regresses; `ed_metal`
is developed against its own probe window and then takes over the world, with an env flag and an A/B
number at each step. Bevy keeps windowing, input, UI, audio, physics and the player.

## 4. Order of work (revised 2026-11-05: native Metal first)

Decision: no wgpu detour and no "spike". Build the Metal backend now, make it fill the GPU, then add
features onto it. Bevy stays for simulation, input, audio, physics and UI; the world is drawn by
`ed_metal`. Delivery pace so far is days, not weeks, so each step below is a day-scale target.

| # | Step | Result | Done when |
|---|---|---|---|
| N0 | **`ed_metal` backend**: device, queues, `CAMetalLayer` window, shader library build (`.metal` via xcrun), executes an `ed_gpu` `CompiledGraph`, heap-aliased transients, per-pass GPU timers from counter sample buffers | A native window clearing and drawing a test pass with per-pass ms | `ed_metal_probe` shows pass timers; graph alias plan used |
| N1 | **GPU-resident world data**: pooled vertex/index/cluster/instance buffers + argument-buffer tables, filled from the existing tile build output (no per-tile objects) | Tiles are copies into pools (old S7, moved first because everything GPU-driven needs it) | 100+ tiles resident, zero per-tile GPU objects |
| N2 | **GPU-driven geometry**: compute frustum + occlusion cull writes an indirect command buffer; terrain clipmap; buildings, props, rocks, trees as instances | One encode per frame regardless of tile count | Draw calls flat vs. tiles; GPU cull < 0.3 ms |
| N3 | **Visibility buffer + material resolve** (tile memory on Apple GPUs) | Geometry drawn once; no prepass | Main-pass cost independent of geometry |
| N4 | **Cached shadows** reading the same GPU instance lists | Shadow cost under 0.8 ms | |
| N5 | **Atmosphere, clouds, post, MetalFX** (own TAAU behind `Upscaler`), dynamic resolution on GPU time | Parity with today's look | |
| N6 | **Cutover**: Bevy renders UI only; delete world meshes/materials from Bevy | One renderer for the world | 60 fps on the 6 reference scenes |
| N7 | Windows backend (D3D12/Vulkan + DLSS/RTX) behind the same `ed_gpu` interfaces | Later, same graph and shaders | |

Utilisation is measured, not assumed: every step reports `tools/gpu_passes.sh` occupancy and per-pass
time, and a step is not done until occupancy is explained (GPU busy for the right reasons).

Integration until N6: the Bevy app owns the window; `ed_metal` renders into the same `CAMetalLayer`
and Bevy's own 3D camera is turned off for the world. World data and camera come from ECS resources
copied once per frame to `ed_metal`'s thread.

## 5. Native Metal timeline

It starts now (N0). G1 no longer exists as a decision; the wgpu path is only kept as the current
renderer until N6. What stays portable: `ed_gpu` (graph, caps, timers), the WGSL/MSL split (shaders
written as MSL now; a translation/DXIL path comes with N7), and the data layout.

## 6. Risks

| Risk | Mitigation |
|---|---|
| Abstraction designed in a vacuum | Metal spike after S1; first features (S2, S3) are the abstraction's real users |
| Two renderers in flight (Bevy + ours) | Every slice has an env flag and an A/B; delete the old path when stable |
| Terrain clipmap mismatches physics heights | Same height function and the existing `TerrainGrid`; a test comparing GPU and CPU sampled heights |
| Floating origin vs. GPU pools | All GPU data in tile-local f32 plus a per-tile f32 offset updated on re-anchor; motion vectors zero the re-anchor jump |
| Headless numbers diverge from windowed | Every perf entry notes which; the gate runs both; a windowed Mac pass closes each slice |
| Determinism (multiplayer) | Render-only; nothing in `ed_render` feeds simulation or generation |
